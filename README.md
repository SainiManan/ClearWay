# ClearWay 🌙

Compare walking routes at night using the safety indicators that are actually
available — and be explicit about the ones that are not.

Built for PS1 (Safe Route Finder for Night Travel) of the OFFGRID hackathon at MUJ.

## What it does

1. You enter a start and a destination.
2. ClearWay resolves both to coordinates (OpenStreetMap Nominatim).
3. It requests candidate **walking** routes (OSM `routed-foot` profile) and
   shows their real distance, duration and geometry on an interactive map.
4. It scores each route on the indicators that have data, and states clearly
   which indicators have none.
5. It explains the trade-off between routes.
6. You can focus a route by clicking it on the map, or with the focus control
   directly beneath the map (clicking a 5px line on a touchscreen is unreliable,
   so both paths set the same selection).

## Honest data status

| Factor | Source | Status |
|---|---|---|
| Route geometry, distance, duration | OpenStreetMap `routed-foot` | **Real**, live |
| Start / destination coordinates | OpenStreetMap Nominatim | **Real**, live |
| Pedestrian infrastructure | OpenStreetMap via Overpass API | **Real**, live |
| Street lighting | `data/sample_lighting.csv` | **Simulated** |
| Reported hazards | `data/sample_hazards.csv` | **Simulated** |
| Route isolation | none | **Unavailable** |

The simulated files are generated by `data/generate_sample_data.py` and are
pseudo-random values. They are **not** municipal data. They only cover the
Jaipur demonstration area declared in `src/data.py`; outside it, indicators are
reported as unavailable rather than extrapolated.

### Why lighting and hazards are simulated

I checked every open source that could supply real data:

- **Street lighting.** OpenStreetMap contains **zero** `lit=*` tags and **zero**
  `highway=street_lamp` nodes anywhere in Jaipur — verified by direct Overpass
  query. The *Street Lights Data Jaipur* dataset on `data.gov.in` /
  `smartcities.data.gov.in` publishes aggregate LED counts, not per-light
  coordinates, and its resource is not publicly downloadable. Other open
  streetlight layers (Englewood CO, Anne Arundel County) are US-only.
- **Reported hazards.** No open pedestrian-incident feed exists. The available
  Indian datasets (NCRB, MoRTH) are state-level aggregates with no coordinates,
  so they cannot be attached to a specific route.
- **Route isolation.** No dataset at all.

Substituting a clearly-labelled simulated dataset is honest. Inventing
lighting coverage would not be.

### Limitation of the real pedestrian data

Footway and sidewalk coverage in Jaipur is sparse in OpenStreetMap. On the demo
route only ~2% of sampled points lie within 25 m of a mapped footway. The factor
therefore measures **what has been mapped**, not ground conditions, and the UI
says so. An unmapped footpath is not proof that no footpath exists.

Overpass responses are cached in `data/.cache/` so the same area is never
queried twice.

### How missing data is handled

- A missing factor is **never** treated as zero risk.
- No score is produced unless at least 50% of the total scoring weight is
  backed by real data. Otherwise the app says why.
- An absence of hazard reports is not evidence that a route is safe.

## Deployment

**Streamlit Community Cloud** is the supported target. Vercel will not work —
it is stateless serverless, while Streamlit needs a persistent Python process
holding a WebSocket for the whole session.

### The routing provider problem (important)

Two providers are supported, selected automatically:

| Provider | Where it works | Key |
|---|---|---|
| OpenRouteService | cloud and local | required (free, instant) |
| OpenStreetMap routed-foot | local only | none |

`routing.openstreetmap.de` is a donated community service that **refuses
connections from datacentre IP ranges**. It works perfectly from a home
connection, which is why the app runs on localhost but fails on Streamlit
Cloud with `Connection refused`. Geocoding keeps working there because
Nominatim accepts cloud IPs, which makes the failure look like a routing bug
rather than a provider restriction.

**To deploy:** sign up free at [openrouteservice.org](https://openrouteservice.org/)
(no credit card), then add the key in Streamlit Cloud under
**Settings → Secrets**:

```toml
OPENROUTESERVICE_API_KEY = "your-key-here"
```

Locally, export it or put it in a `.env`:

```bash
export OPENROUTESERVICE_API_KEY="your-key-here"
```

The app names the provider it actually used in the
"Data sources, coverage and limitations" panel, so a deployment can never
silently claim a provider it is not using. A template lives at
`.streamlit/secrets.toml.example`; the real secrets file is git-ignored.

### Unknown risk to check after deploying

Overpass (`overpass-api.de`), used for the real pedestrian-infrastructure
factor, is also a community service and may reject cloud IPs in the same way.
If it does, that factor degrades to "unavailable" and coverage drops to 65%
rather than the app failing — but confirm it after deploying, because the
failure was never observed from a cloud host.

## Design

Two layers, deliberately separated:

1. **`.streamlit/config.toml`** sets the base dark theme. This is Streamlit's
   supported theming mechanism, so the app looks coherent without fighting
   Streamlit's own defaults.
2. **`assets/theme.css`** adds the parts Streamlit gives no control over — the
   hero, the search panel, metric rows, risk chips, provenance lists and
   spacing. It is injected once by `src/theme.load_theme()`.

The stylesheet uses Streamlit's stable `data-testid` attributes rather than
generated class names, which change between releases. A missing stylesheet is
non-fatal: the app falls back to the config theme alone.

The map uses a dark Esri basemap (`World_Dark_Gray_Canvas`, no API key) so the
route colours stay readable and the map matches the rest of the UI.
CartoDB `dark_matter` was tried first but now requires an API key, which would
have silently rendered a blank map.

## Setup

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
```

If PowerShell blocks activation, use Command Prompt:

```cmd
.venv\Scripts\activate.bat
```

On macOS or Linux:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
```

## Run

```bash
streamlit run app.py
```

Then open <http://localhost:8501>.

## Test

```bash
python -m pytest
```

## Suggested demo locations

Both endpoints must be inside the Jaipur demonstration area for the simulated
indicators to apply.

- `Hawa Mahal, Jaipur` → `Jaipur Junction railway station`
- `Johari Bazaar, Jaipur` → `Hawa Mahal, Jaipur`
- `Manipal University Jaipur` → `Sanganer, Jaipur`

Searching somewhere outside the region (for example `India Gate, New Delhi` →
`Connaught Place, New Delhi`) still shows real routes and distance, but the app
withholds the score and explains that no indicator data exists there. This is
intentional and demonstrates the missing-data handling.

## Scoring model (illustrative)

```
Score = (0.35·L + 0.25·P + 0.30·H + 0.10·I) / coverage
```

Weights are prototype assumptions, **not** validated coefficients. The result
is renormalised over the factors that have data. Thresholds: below 30 lower,
30–60 moderate, 60 and above higher estimated risk.

## Disclaimer

ClearWay provides estimates based on available data. It cannot guarantee
personal safety. Missing or outdated data may affect route assessments. This is
a hackathon prototype, not safety advice.
